# RFC 0001：IMOS MVP

- 状态：已接受
- 跟踪 issue：#1
- 创建日期：2026-08-29

## 摘要

IMOS（Immutable Object Store）为上层系统提供确定性的制品下载、安装、复用和垃圾回收能力。

MVP 是一个本地 Rust 命令行程序。一次性 CLI 可以提交已有的不可变 Plan 文件；stdio 服务接收完整 Plan JSON Value，由 IMOS 确定性编码并在上层 `home` 中原子创建文件。IMOS 使用 hard link 追踪 Plan 文件是否仍然存活，使用 SQLite 保存最小意愿关系，以文件系统上的最终路径表达下载和安装结果。临时路径、原子 rename 和文件锁共同保证并发与崩溃安全。

## 背景

包管理器、开发环境管理器和构建工具经常重复实现以下能力：

- 下载并校验远程制品；
- 防止多个进程重复下载或产生半成品；
- 解包或安装文件到稳定目录；
- 在多个上层索引之间复用结果；
- 在没有任何上层系统需要结果时安全回收。

IMOS 将这些职责下沉为独立基础设施。它不解析包依赖，不进行版本求解，也不决定 key 的结构。上层系统负责生成确定性 key，IMOS 负责维护 key 与不可变结果之间的稳定绑定。

## 目标

MVP 必须提供：

1. 通过不可变 plan 文件声明安装意愿；
2. 按下载 key 复用原始下载字节；
3. 按 plan key 复用完整安装目录；
4. HTTP、HTTPS 和本地文件下载来源；
5. 可选的下载大小和 SHA-256 校验；
6. tar、tar.gz 和 tar.zst 归档处理；
7. 普通文件和可执行文件安装；
8. 跨进程的首次执行者选择与进度观察；
9. 根据所有存活 plan 意愿执行垃圾回收；
10. 失败和崩溃后不暴露不完整结果。

## 非目标

MVP 不提供：

- 用户级和系统级两层 store；
- 远程、多主机或 P2P 缓存；
- 后台守护进程；
- 包依赖或版本求解；
- 自动容量配额和 LRU 策略；
- 不同 key 之间的内容去重；
- 符号链接或 hard link 归档项的安装；
- 网络文件系统支持；
- Windows 支持。

## 术语

- **request**：一个位于上层 `home` 中、由 IMOS 管理落盘的不可变 Plan 文件及其 inode；一次性 CLI 也可提交符合相同约束的已有文件。
- **plan key**：上层系统提供的透明字符串，代表完整安装结果的确定性。
- **download key**：上层系统提供的透明字符串，代表下载字节的确定性。
- **意愿**：一个仍然存活的 request 声明它需要某个 plan key。
- **发布**：将完整临时对象原子 rename 到最终路径。
- **首次执行者**：获得某个 key 独占文件锁、负责产生结果的进程。

## 核心不变量

1. 同一 request inode 永远表达同一份 plan；意愿变化必须创建新 inode。
2. 同一 plan key 永远代表相同安装结果。
3. 同一 download key 永远代表相同下载字节。
4. SQLite 只记录意愿关系，不记录结果是否存在或操作是否活跃。
5. 下载最终路径存在，表示下载对象已完整发布。
6. 安装最终路径存在，表示安装结果已完整发布。
7. 只有 `tmp` 中允许出现半成品。
8. 已发布对象不允许原地修改。
9. 文件锁只对遵守 IMOS 协议的进程生效，store 不允许被外部直接修改。

上层系统负责 key 的正确性。IMOS 发现相同 key 对应冲突的已知约束时必须报错，但不尝试从 plan 或下载内容派生 key。

## 外部接口

MVP 暴露三个命令：

```text
imos --store <path> create <plan-file>
imos --store <path> remove <plan-file>
imos --store <path> gc
```

`--store` 省略时使用平台用户缓存目录下的 `imos`。成功命令通过 stdout 输出机器可消费的最终结果，进度和诊断写入 stderr。

### create

`create` 读取、校验并实现 plan：

1. 验证 plan 文件是普通文件；
2. 验证 plan 文件与 store 位于同一文件系统；
3. 验证新 request 在注册前只有一个 link；
4. 解析 IMOS 基础部分；
5. 获取全局 GC 共享锁；
6. 获取 plan key 独占锁；
7. 下载并执行所有 item；
8. 原子发布安装结果；
9. 在 `requests/` 中创建指向 plan 文件的 hard link；
10. 在 SQLite 事务中提交意愿关系；
11. 输出安装结果的 `root` 路径。

同一 inode 重复执行 `create` 必须幂等。相同 plan key、不同 inode 表示多个独立意愿，并复用同一个安装结果。

只有安装结果成功发布后才能提交意愿。失败过程中已经完整发布的下载对象可以保留为缓存。

### remove

`remove` 根据 plan 文件 inode 删除 SQLite 中对应 request，并删除 store 内部 hard link。它不删除上层 plan 文件，也不立即删除下载或安装结果。

如果上层直接删除 plan 文件而没有调用 `remove`，`gc` 必须通过 `nlink` 发现并清理失效意愿。

### gc

`gc` 获取全局独占锁：

1. 清理只有内部 hard link 的失效 request；
2. 清理没有 SQLite row 的孤立内部 hard link；
3. 从 SQLite 计算存活 plan key 集合；
4. 计算存活 plan 所依赖的 download key 集合；
5. 删除不在存活集合中的安装对象；
6. 删除不在存活集合中的下载对象；
7. 清理未被锁定的临时对象。

任何无法确认安全性的对象都必须保留。GC 可以多次运行并得到相同结果。

## Plan 文件

一次性 CLI 的 Plan 文件必须在 `create` 前完成写入。stdio Install 请求则提交 `{ id, home, plan }`，其中 `plan` 是完整 JSON Value；IMOS 使用 `serde_json::from_value` 提取自身理解的结构，使用 `serde_json::to_vec` 确定性编码完整 Value，并在 `home` 中创建全新的临时 inode，完整写入后原子替换 `home/<plan.name>`。IMOS 不比较新旧内容；即使内容相同，每次 Install 也会替换 inode，内容与 key 的确定性关系由上层负责。同一目标文件的请求通过路径锁串行执行。被替换的旧 inode 若仍有 IMOS 内部 hard link，其 `nlink` 会降为 1，后续由 GC 清理。此后已发布文件只允许 unlink，不允许原地修改。IMOS 为该文件创建内部 hard link，因此 `home` 与 store 必须在同一文件系统。

Plan 不使用额外 envelope。IMOS 理解的版本化字段直接位于 JSON 顶层；其他顶层字段属于上层系统，IMOS 不解释但会保留在落盘文件中。

```json
{
  "version": 1,
  "name": "example-plan.json",
  "key": "example-plan-key",
  "items": [
    {
      "name": "Tool archive",
      "key": "example-download-key",
      "kind": {
        "type": "UnpackDir",
        "url": "https://example.invalid/tool.tar.zst",
        "size": 123456,
        "digest": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
        "archive": "TarZstd",
        "strip": 1,
        "to": "."
      }
    }
  ],
  "upstream": {
    "name": "example"
  }
}
```

IMOS 基础 shape 为：

```text
Plan {
  version: 1,
  name: String,
  key: Key,
  items: [Item]
}

Item {
  name: String,
  key: Key,
  kind: ItemKind
}
```

`version` 不受支持、key 或 name 无效、字段类型错误时必须拒绝。Plan 顶层允许未知扩展字段；Item 和 ItemKind 继续拒绝未知字段。Plan name 同时用作文件名，必须是 1 到 64 个 UTF-8 字节的单个安全路径组件。上层扩展字段不能影响 IMOS 安装结果，但属于 request 确定性内容的一部分。

### 下载约束

MVP 支持 `http`、`https` 和 `file` URL。

`size` 表示原始下载字节数。`digest` 格式为 `sha256:<64 个小写十六进制字符>`，同样作用于原始下载字节。两者都是可选断言，不承担对象寻址职责。存在断言时，无论首次下载还是复用已有下载对象，都必须校验；不匹配时报告 key 冲突或缓存损坏，不得覆盖已有对象。

### PlanItem

MVP 支持四种 action。

#### UnpackDir

```text
{
  type: "unpack_dir",
  kind: "tar" | "tar_gzip" | "tar_zstd",
  strip: u32 = 0,
  to: RelativePath = "."
}
```

将归档中的目录树去掉前 `strip` 个路径组件后安装到 `root/<to>`。

#### UnpackFile

```text
{
  type: "unpack_file",
  kind: "tar" | "tar_gzip" | "tar_zstd",
  from: RelativePath,
  to: RelativePath
}
```

从归档中选择一个普通文件并安装到 `root/<to>`。匹配不到或匹配多个条目时失败。

#### InstallFile

```text
{
  type: "install_file",
  to: RelativePath
}
```

将原始下载字节安装为 `root/<to>`，权限规范化为 `0644`。

#### InstallBin

```text
{
  type: "install_bin",
  name: FileName
}
```

将原始下载字节安装为 `root/bin/<name>`，权限规范化为 `0755`。

### 路径和归档安全

所有 plan 路径必须是 UTF-8 相对路径，禁止空组件、`.` 以外的特殊组件、`..`、绝对路径和平台前缀。目标之间发生文件冲突时失败，不允许后项覆盖前项。

归档只接受目录和普通文件。符号链接、hard link、设备、FIFO 及其他特殊条目必须拒绝。目录权限规范化为 `0755`；普通文件根据归档可执行位规范化为 `0755` 或 `0644`。IMOS 不保留归档时间戳、所有者、组、ACL 或扩展属性。

## Store 布局

Key 是透明字符串，不能直接拼入路径。MVP 使用 key 的 SHA-256 小写十六进制编码作为物理名称，并在对象中保存原 key 供检查。

```text
store/
├── state.sqlite
├── requests/
│   └── <request-inode>
├── dl/
│   └── <sha256(dl-key)>/
│       ├── key
│       └── data
├── install/
│   └── <sha256(plan-key)>/
│       ├── key
│       └── root/
├── locks/
│   ├── gc
│   ├── dl/<sha256(dl-key)>
│   └── install/<sha256(plan-key)>
└── tmp/
```

对象目录必须和 `tmp` 位于同一文件系统，保证 rename 原子性。store 根目录必须只允许其所有者访问。

## SQLite 意愿索引

SQLite 只保存两类关系：

```sql
CREATE TABLE request_plans (
    request_ino TEXT PRIMARY KEY,
    plan_key    TEXT NOT NULL
) STRICT;

CREATE INDEX request_plans_by_plan
    ON request_plans(plan_key);

CREATE TABLE plan_downloads (
    plan_key TEXT NOT NULL,
    dl_key   TEXT NOT NULL,
    PRIMARY KEY (plan_key, dl_key)
) STRICT, WITHOUT ROWID;
```

`request_ino` 使用无符号十进制文本，避免 SQLite 有符号整数范围限制。由于 hard link 要求同一文件系统，inode 在单个 store 中足以标识 request。

完整 plan 来自 `requests/<request-inode>` hard link 文件；SQLite 不重复保存 plan。实际结果是否存在始终由文件系统最终路径决定。

SQLite 启用外键检查、WAL 和完整同步。关系更新使用短写事务，下载和解包期间不持有 SQLite 写事务。

## 锁与进度

`locks/gc` 是永久文件。`create` 和 `remove` 持有共享锁，`gc` 持有独占锁。

每个 download key 和 plan key 有一个永久锁文件。首次执行者获得独占锁后，先重新检查最终对象是否已存在，再决定执行。等待者可以读取锁文件中的进度；进程退出时操作系统自动释放锁。

锁文件在一次操作开始时截断，并在该次操作中以 JSON Lines append-only 写入：

```json
{"event":"started"}
{"event":"download","current":1048576,"total":8388608}
{"event":"unpack"}
{"event":"completed"}
```

失败以 `failed` 终态表达。崩溃可能留下不完整的最后一行，读取者必须忽略它。锁文件不能在普通操作中删除，避免不同进程锁住不同 inode。

## 原子发布和崩溃恢复

下载和安装使用相同协议：

1. 在 `tmp` 创建唯一目录；
2. 完成全部写入和验证；
3. 写入原 key；
4. 关闭并同步必要文件；
5. 原子 rename 到最终目录。

崩溃发生在 rename 前，只留下临时对象；发生在 rename 后，留下完整可复用对象。SQLite 不记录对象完成状态，因此不会出现已提交的完成 row 指向不存在对象的问题。

`create` 在安装结果发布后才提交 request 意愿。SQLite 提交前崩溃可能留下完整但未引用的缓存和孤立 request hard link；GC 必须安全清理它们。

## 安全与平台约束

MVP 仅支持具有可靠 hard link、advisory file lock 和同文件系统原子 rename 语义的本地 Unix 文件系统。

必须防御：

- plan 路径逃逸；
- tar 路径穿越和特殊条目；
- key 路径注入；
- 下载大小或摘要冲突；
- 临时文件被最终结果误认；
- GC 与 create/remove 并发；
- 相同 key 的并发发布。

## 验收标准

1. 首次 create 下载并安装一个本地或 HTTP 制品；
2. 重复 create 相同 inode 幂等；
3. 两个 request 使用相同 plan key 时只保留一个安装结果；
4. 不同 plan 共享 download key 时复用下载；
5. size 或 digest 不匹配时不发布下载；
6. 两个进程并发创建相同 plan 时只产生一个完整结果；
7. 失败和崩溃不产生可见半成品；
8. remove 不立即删除结果；
9. 删除外部 plan 文件后，GC 识别 `nlink == 1` 并回收对应结果；
10. 仍被任一 request 需要的 plan 和 download 不被 GC；
11. 非法归档路径和链接条目被拒绝；
12. 全部 Rust 测试、格式化和静态检查通过。
